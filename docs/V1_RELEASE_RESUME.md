# נקודת המשך — שחרור ייצור והתראות V1

עודכן: 14.10.2026, Asia/Jerusalem. זהו מסמך הכניסה לסשן הבא של המשימה.
במקרה של סתירה עם דיווחים מוקדמים ב־HANDOFF או בדוח הספרינט, ההנחיות והמצב העדכניים שלהלן הם הקובעים.

## סגירת הגרסה הקיימת — בקשה עדכנית

המשתמש חידש את הביצוע והורה לרכז גם את Collections.tsx, CreditTransactions.tsx וכל התיעוד הלא שמור ב־main המקומי.
נדרש commit בבחירת קבצים מפורשת, מיזוג fast-forward בלבד ב־worktree של main, build אחד ובדיקת גבייה ממוקדת.
לא נדרש פיתוח חדש או הרצה חוזרת של כל הספרינט. לאחריהם יש לבדוק Supabase, להחיל רק את שתי המיגרציות החסרות ולאמת התקנה.
בוצע fetch: origin/main עדיין 6120757, origin/feature עדיין 07c9aad; אין פיצול מול feature הנוכחי f2cece2. ה־worktree של main נקי.
הכלל הישן להוציא את עבודת הגבייה מה־commit הוחלף בבקשה לכלול אותה. אין שינוי בכלל החרגת סודות, ENV ותוצרי בדיקה.
**אין push עד להצגת diff מלא ועדכני מול origin/main וקבלת אישור מפורש.** הנתונים הפיקטיביים אינם נמחקים או מאופסים.
הסעיפים הבאים מתארים את נקודת העצירה הקודמת; תוצאות סגירה חדשות יתווספו בסוף המסמך לאחר הביצוע.

## איפה עצרנו

הפיתוח ושני התיקונים האחרונים נשמרו ב־Git ועברו בדיקות מקומיות. התקנת המסד **לא התחילה**:
קריאת קדם דרך חיבור Supabase נכשלה ב־connection timeout, והמשתמש הורה לעצור בכשל.
לא נשלחה אף קריאת `apply_migration`. שתי המיגרציות עדיין ממתינות, ולא בוצעו בדיקות לאחר התקנה.
אין push או פריסה חדשים. הענף הנוכחי הוא `feature/v1-production-task-permissions`.

**הפעולה הראשונה בהמשך:** לאחר שהמשתמש מבקש לחדש את הביצוע, לבדוק את חיבור Supabase בקריאה בלבד,
לאמת מחדש אילו מיגרציות מותקנות, ולהמשיך מהתקנת המיגרציה הראשונה רק אם בדיקת הקדם תקינה.
אין צורך להתחיל את הפיתוח מחדש או לשחזר את השינויים מה־diff.

## ההרשאות וההחלטות שנשארות בתוקף

- המשתמש אישר לבצע ספרינטים 1 + 2 יחד: סגירת גרסת הקוד והחלת שתי המיגרציות, כולל בדיקות לאחריהן.
- המשתמש הבהיר שהנתונים פיקטיביים, קיבל את הסיכון לאובדנם וביטל במפורש את דרישת הגיבוי. **גיבוי אינו תנאי להמשך.**
- אין למחוק או לאפס נתונים בכוונה. אין `reset`, `clean` או דריסה של העבודה הקיימת.
- אפשר לעדכן main המקומי תוך שמירת כל השינויים הקיימים.
- בכשל התקנה או בדיקה יש לעצור ולדווח. אין להמשיך למיגרציה הבאה או לבצע ניסיונות תיקון חיים ללא המשך מתאים מהמשתמש.
- **אין push או פריסה עד להצגת diff מלא ואישור מפורש של המשתמש.** דחיפת main מפעילה פריסה אוטומטית ב־Cloudflare.
- הרשאות המסכים והזרימה העסקית הקיימות נשמרות; אין שינוי Make/iCredit או שליחת הודעות חיצוניות.
- בדיקת Supabase Auth/PostgREST מלאה בסביבה מבודדת חסומה. המשתמש ביקש לתעד זאת ולהשלים את יתר ההכנה.

הוראות ישנות המחייבות גיבוי לפני ההתקנה הוחלפו בהנחיה המפורשת לעיל. האישור הקיים להתקנת שתי המיגרציות נשמר;
הבקשה הנוכחית לתיעוד אינה חידוש של ההתקנה שנעצרה.

## מה נכשל, ולמה עדיין אין תיקון מאומת

### הכשל שעצר את ההתקנה

בקריאת `production-v1-preflight.sql` דרך Supabase MCP התקבלה תגובת isError:

```text
upstream connect error or disconnect/reset before headers.
reset reason: connection timeout
```

התגובה מצביעה על כשל בנתיב החיבור; הסיבה המדויקת לתקלה לא אומתה. אין הוכחה לכשל SQL או לכשל במיגרציה.
קריאת הקדם הייתה לקריאה בלבד, ולאחריה לא נשלחה אף מיגרציה. אין צורך בתיקון rollback של התקנה שבוצעה בסשן זה.
בהתאם להוראה לעצור בכשל, לא נעשה ניסיון חוזר. הטיפול הבא הוא אימות חיבור מחדש ובדיקת קדם, לפני כל DDL.

### כשל נפרד בחיבור הישיר, במהלך הכנת הגיבוי

נמצא `DATABASE_URL` ב־`.env.local`, עם Session pooler של הפרויקט. לאחר הוספת תעודת Supabase ואימות TLS,
המסד דחה את הסיסמה ב־`28P01: password authentication failed`.
לא שונו קובצי ENV, לא אופסה סיסמת מסד ולא בוטל אימות TLS.

זהו כשל נפרד מה־timeout של MCP. חיבור MCP המאומת יכול לבצע התקנה בלי הסיסמה שב־DATABASE_URL.
אם יהיה צורך בחיבור ישיר, יש לעדכן מקומית סיסמת מסד תקינה; אין להדפיס או לצרף את כתובת החיבור למסמכים/ל־Git.
אין להתחיל איפוס סיסמה כתיקון ל־timeout בלי ראיה שזה נדרש ובלי הנחיה מתאימה מהמשתמש.

## סדר הפעולות לפעם הבאה

1. לקרוא מסמך זה ו־HANDOFF. לוודא שהמשתמש מבקש לחדש את הביצוע אחרי העצירה.
2. לבדוק status, index, commits ו־worktrees. לשמר את עבודת הגבייה ואת התיעוד הלא שמור; לא לנקות אותם.
3. לבדוק את חיבור Supabase בקריאה בלבד: `get_project`, שאילתת `select 1` קצרה ו־`list_migrations`.
   אם יש כשל נוסף — לעצור ולדווח עם תגובת הכלי; אין לבצע DDL.
4. אם החיבור תקין, לבדוק מחדש שאין התקנה חלקית או שינוי סכמה, ואז להריץ
   [production-v1-preflight.sql](../scripts/production-v1-preflight.sql). לשמור את תוצאות המונים וטביעות הנתונים.
5. להתקין באמצעות `apply_migration` את מיגרציית ההרשאות. לוודא הצלחה לפני התקנת מיגרציית ההתראות.
   אם הכלי יוצר version שונה משם הקובץ המקומי, לתעד את המיפוי ולהסדיר את התאמת היסטוריית המיגרציות לקבצים לפני השחרור.
6. להתקין את מיגרציית ההתראות. בכשל — לעצור ולדווח איזו מיגרציה כבר הותקנה ואילו אובייקטים נוצרו; לא להריץ שוב בעיוורון.
7. להריץ [production-v1-post-install.sql](../scripts/production-v1-post-install.sql), ולהריץ שוב את סקריפט הקדם להשוואת טביעות הנתונים.
   לצפות למשימה פעילה אחת לכל פריט זכאי, בלי חסרים/כפילויות, ללא קריאות או אירועי ייצור שנוצרו בטעות באתחול,
   עם RLS, שבעת הטריגרים והרשאות RPC תקינות. אם טביעה השתנתה, לבדוק את הסיבה ולא להכריז על שימור נתונים אוטומטית.
8. לבדוק קריאה בהרשאות authenticated עבור OFFICE/admin ו־SALES, ללא כתיבה עסקית קבועה; לבדוק advisors ולהבחין בין ממצאים קיימים לחדשים.
   אין לסמן בדיקת SQL תחת authenticated כבדיקת Supabase Auth/PostgREST מלאה.
9. לעדכן את הדוח, HANDOFF ומסמך זה לפי תוצאות בפועל. לשמור את התיעוד ב־commit ייעודי בלי עבודת הגבייה.
10. לאחר הצלחת המסד והבדיקות, לעדכן main המקומי ב־worktree המתאים. ליצור diff מלא מול main המרוחק המעודכן,
    להציג למשתמש מה ייכלל ולחכות לאישור מפורש ל־push ולפריסה.
11. רק לאחר אותו אישור: לבצע את ספרינט 3 — push ל־main, בדיקת הפריסה ובדיקות משתמש במערכת שנפרסה.

[production-v1-quiesce.sql](../scripts/production-v1-quiesce.sql) הוא תוכנית עצירת נתיבי V1 ששומרת את המידע;
הוא אינו גיבוי או rollback מלא, ואין להפעילו אוטומטית בעקבות כשל חיבור.
