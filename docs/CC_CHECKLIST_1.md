# צ'ק-ליסט ביצוע — תהליך הזמנה מלא (מערכת קאירי)

> מסמך זה מיועד ל-Claude Code (CC). עוברים עליו **שלב אחר שלב**, עם עצירה לאישור בסוף כל משימה. אין להתקדם למשימה הבאה בלי אישור מפורש ממרקו.

---

## חלק א' — עקרונות ההטמעה

### עקרון-על

המערכת צריכה להיות **כמעט זהה לתהליך שמתבצע היום**, רק בצורה נוחה יותר. **לשקף את המציאות הקיימת — לא לשפר, לא להוסיף תחכום.** שיפורים יבואו רק אחרי שהמערכת עובדת בפועל.

### חצי-אוטומטי (קריטי)

שום שינוי סטטוס לא מתבצע אוטומטית. כשהתנאים מתקיימים, המערכת **מציעה** למשתמש לשנות סטטוס (באנר / דיאלוג לא-חוסם) — והמשתמש **מאשר או דוחה**. זהו המשך ישיר של גישת ה-warn-and-override הקיימת: המערכת לא כופה, היא מציעה.

### אחריות = כוכב הצפון

כל פעולת משתמש מקבלת חותמת זמן (מי, מה, מתי) ב-`order_status_history`. אין פעולה בלי עקבה.

### כללי עבודה ל-CC

- **בקש אישור לפני כל שינוי בקוד.** הצג תוכנית → קבל אישור → בצע.
- **שלב אחד בכל פעם, עצירה לאישור.** אין לבנות כמה משימות בבת אחת.
- **ציין בדיוק אילו קבצים משתנים** — רשימה מפורשת, לא "החלף את src".
- **היזהר מקבצים בעלי שמות דומים** (למשל `printOrder.ts` מול `PrintOrder.tsx`).
- **שאילתות `profiles` מ-`orders`** — תמיד עם FK מפורש: `profiles!orders_agent_id_fkey(full_name)`.
- **מיגרציות דרך קבצי migration בלבד**, לא דרך Supabase UI.
- **`git commit` לפני כל פעולה מסוכנת.**
- הכל בעברית, RTL. פונקציונליות לפני עיצוב.

### מבנה הסטטוסים היעד

```
הזמנה: quote → ממתין לגבייה → ייצור → מוכנה → נאסף ע"י מתקין → הותקן → הושלמה  (+ בוטלה)
פריט (רק בזמן "ייצור"): חדש → נגזר → במתפרה → מוכן  (+ בוטל)
```

### שלושה מישורים

1. **מישור הזמנה** — ההזמנה כיחידה אחת.
2. **מישור פריט** — קיים **רק** כשההזמנה ב"ייצור". פריטים רצים במקביל, כל אחד עם חותמת תאריך.
3. **מישור התקנה** — "הכל או כלום" לכל ההזמנה יחד. מתחיל רק כשההזמנה "מוכנה".

## בדיקת E2E מלאה (04/08/2026) — ✅ בוצעה

`npm run build` עבר נקי. הורצה הזמנת-בדיקה אמיתית (`__E2E_TEST__`) דרך Playwright מול הפרודקשן בפועל, על כל הזרימה המלאה: יצירה (משימה 2) → בחירה סופית במשרד (משימה 3) → ניתוב פר-פריט (משימה 4) → קידום כל פריט לאורך המסלול שלו, פנימי וחיצוני (משימה 5) → טריגר 6/6 (משימה 6) → שיוך מתקין (משימה 7, כולל הוספת מתקין דרך מסך ההגדרות החדש) → חתימה כפולה (משימה 8) → גביית יתרה + סגירה (משימה 9) → יומן פעילות (משימה 10). ההזמנה סיימה בסטטוס `completed` עם שתי החתימות ותשלום נרשם. **אפס שגיאות קונסולה** לאורך כל הריצה. כל נתוני הבדיקה נוקו מה-DB בסיום (הזמנה, פריטים, יומן, לקוח, מתקין-בדיקה).

**באג אמיתי נמצא ותוקן:** `src/pages/orders/ItemSelectionDialog.tsx` — הרכיב תמיד נפתח עם 0 פריטים מסומנים במקום לשקף את `for_execution` בפועל, כי ה-`useState` הפנימי אותחל פעם אחת ב-mount ולא סונכרן מול `open`/`items`. אומת בפועל: הזמנת-בדיקה ראשונה נשמרה עם שני הפריטים ב-`for_execution: false` למרות שסומנו "לביצוע" בטופס. **תוקן** בהוספת `useEffect` שמסנכרן את הבחירה בכל פתיחה (אותו פאטרן שכבר היה נכון ב-`ItemAdvanceDialog`). אומת מחדש לאחר התיקון — עובד נכון גם ב-`NewOrder` וגם ב-`OrderDetail`.

שאר "הכשלים" שנרשמו במהלך הריצות היו סלקטורים לא-חד-משמעיים בסקריפט הבדיקה עצמו (טקסט "פעילות"/"נאסף ע\"י מתקין" שהתאים ליותר מאלמנט אחד) — אומתו כתקינים ידנית דרך צילומי מסך ושאילתות SQL ישירות.

חלק ג' (WhatsApp חיצוני, תפקידי מערכת נוספים, תיאום התקנה מלא, קיבוץ לפי אזור) נשאר נדחה במפורש עד אישור מרקו.
