# מסמך ארכיטקטורה — מערכת Kairi Curtains המאוחדת
**גרסה 1.1 | מעדכן ומחליף את גרסה 1.0 | Marco Kairi / Kairi Curtains**

מסמך זה משקף את כל ההחלטות שנסגרו מאז גרסה 1.0, על בסיס: גיליונות ההזמנות הקיימים, האבטיפוס של טופס ההזמנה ומסך המעקב, ותשובותיך.

## 1. יומן החלטות שנסגרו

| # | החלטה | פירוט |
|---|---|---|
| 1 | **אין מנוע תמחור** | הסוכן מקליד מחיר (עלות ₪) לכל פריט ידנית. "חישוב אוטומטי" = סכום עלויות הפריטים המסומנים "לביצוע" בלבד. כפתור "מלא" מעתיק את הסכום לשדה "סה"כ לתשלום", והסוכן רשאי לדרוס |

| 3 | **ישות אחת: order** | הצעת מחיר והזמנה הן אותה ישות; ההבחנה בסטטוס. נקבע בדיאלוג הסיום: "בקשה לגבייה + העברה לביצוע" או "הצעת מחיר (לא לביצוע)" |

| 5 | **"לביצוע" פר פריט** | פריט יכול להירשם בטופס ולא להיכנס לביצוע; סיכומים ושריון מלאי מתחשבים רק בפריטים לביצוע |
| 6 | **סטטוס פר פריט + פר הזמנה** | סטטוס ההזמנה הכולל נגזר מסטטוסי הפריטים ומשלב הגבייה |
| 7 | **מספור רץ מ-9000** | מוקצה בשרת בעת סנכרון. טופס שנוצר אופליין מקבל מזהה טיוטה זמני עד לסנכרון |
| 8 | **חתימה מוקלדת** | שדה טקסט (שם החותם), מוטמע ב-PDF. חתימת-מגע (canvas) — הרחבה עתידית |
| 9 | **ניהול מלאי מלא** | בשיטת שקילה, לפי גלילים, עם יומן תנועות append-only. שריון אוטומטי מהזמנות |
| 10 | **אופליין פרגמטי (PWA)** | קטלוג בדים זמין לעיון אופליין; טפסים נשמרים כטיוטה מקומית ומסתנכרנים. PDF ושליחה — אונליין בלבד |
| 11 | **עברית בלבד, RTL** | ללא תשתית ריבוי שפות |
| 12 | **תשלומים** | "שולם על החשבון" בעת היצירה = רשומת תשלום ראשונה בטבלת payments; "נשאר לתשלום" תמיד מחושב, לעולם לא מוקלד |

## 2. מודל הסטטוסים

### סטטוס הזמנה (נגזר + שלבי גבייה)
```
טיוטה (אופליין/לא נשלחה)
   │  שליחה: "הצעת מחיר"          שליחה: "בקשה לגבייה + ביצוע"
   ├──────────▶ הצעת מחיר              │
   │              │ (אושרה)            ▼
   │              └──────────▶ ממתין לגבייה
   │                                   │ (התקבל תשלום/אישור משרד)
   │                                   ▼
   │                            חדש לביצוע
   │                                   │ (פריט ראשון נכנס לעבודה)
   │                                   ▼
   │                                בייצור
   │                                   │ (כל הפריטים לביצוע הושלמו)
   │                                   ▼
   │                                הושלם
   └── בכל שלב: מבוטל
```
טאבי מסך ההזמנות (כמו באבטיפוס): הצעות מחיר / ממתין לגבייה / חדש לביצוע / בייצור / הושלמו / כל ההזמנות + חיפוש לפי שם לקוח + דוח יומי.

### סטטוס פריט (ברירת מחדל, ניתן להתאמה בהגדרות)
`חדש → נגזר → בתפירה/בהרכבה → מוכן → הותקן` (+ מבוטל). המעבר ל"נגזר" הוא אירוע המלאי (ניכוי מגליל). רשימת הסטטוסים תנוהל בטבלת הגדרות כדי שתוכלו לשנות בלי קוד.

## 3. סכמת Database ברמת שדות

### זהות והרשאות
**users_profiles** — id (FK auth), full_name, phone, role (admin/office/sales/viewer), is_active.

### CRM
**leads** — id, external_id (מפתח Google Sheets), full_name, phone, city, source, status, assigned_to→users, notes, created_at, converted_customer_id.
**customers** — id, full_name, phone, phone2, email, address, city, notes, lead_id, created_at.

### קטלוג ומלאי
**fabrics** — id, name, sku, barcode, supplier, color, gsm, weight_per_meter, roll_width, composition, price_per_meter, is_stock_managed (bool), low_stock_threshold_m, is_active.
**fabric_images** — id, fabric_id, storage_path, is_primary, sort_order.
**tags** / **fabric_tags** — תגיות many-to-many.
**fabric_rolls** — id, fabric_id, roll_barcode, received_weight, received_meters, location, status (active/depleted), received_at.
**stock_movements** — id, roll_id, movement_type (receipt/consumption/adjustment/waste/return), quantity_meters (+/-), order_item_id (nullable), weight_measured (nullable, לשקילות), created_by, created_at, note. **append-only; אין UPDATE/DELETE. מלאי גליל = סכום תנועותיו.**

### הזמנות
**orders** — id, order_number (רץ, מוקצה בשרת מ-9000; NULL בטיוטה), is_quote (bool), status, customer_id, agent_id→users, address_snapshot, phone_snapshot, items_total (מחושב), installation_fee, discount, final_total (שדה "סה"כ לתשלום" — ידני עם כפתור מלא), send_email, signature_name, notes, total_width_m (מחושב), created_at, sent_at, legacy (bool למיגרציה).
**order_items** — id, order_id, family ('curtain'/'shading'), item_subtype (לזברה/ונציאני/רומי/גלילה), location (מיקום), width_cm, height_cm, fabric_id (nullable — או טקסט חופשי fabric_text כשהבד לא מהקטלוג), price (עלות ₪ ללקוח), for_execution (bool "לביצוע"), item_status, estimated_meters (צריכת בד לשריון), notes, sort_order,
ושדות פר משפחה (עמודות ייעודיות, לא JSON — כי יש בדיוק שתי משפחות יציבות):
- וילון: sewing_type (סוג תפירה), hem (מכפלת), shtaif (שטייף), is_split (חצוי).
- הצללה: mount_type (רגלי קיר/תקרה), mechanism_side (צד מנגנון), color_fabric (צבע/סוג בד).

*הערה: רגלי קיר/תקרה + צד מנגנון חסרים באבטיפוס הנוכחי — מוחזרים בטופס החדש (קריטי לייצור).*

**payments** — id, order_id, amount, method (מזומן/אשראי/העברה/צ'ק/ביט...), paid_at, received_by, note. יתרה = final_total − Σ payments.
**order_status_history** — id, order_id, order_item_id (nullable), from_status, to_status, changed_by, changed_at, note.

### מסמכים ותקשורת
**documents** — id, order_id, doc_type (quote/order/daily_report), doc_number, storage_path, created_by, created_at.
**communications** — id, customer_id, order_id (nullable), channel (whatsapp/email/call), direction, document_id (nullable), status (sent/failed), sent_by, sent_at.

### מערכת
**settings** — key/value: מונה הזמנות (התחלה 9000), פרטי עסק ל-PDF, מע"מ אם רלוונטי, רשימות ערכים (סוגי תשלום, סטטוסי פריט, סוגי תפירה).
**audit_log** — משתמש, פעולה, טבלה, record_id, לפני/אחרי (JSON). חובה על: מחיקות, שינויי מחיר אחרי שליחה, תנועות התאמה במלאי.

**RLS עקרוני:** sales רואה ויוצר את ההזמנות/לידים שלו וקורא קטלוג; office הכול חוץ ממחיקות וניהול משתמשים; admin הכול; viewer קריאה בלבד. תנועות מלאי — יצירה בלבד, ללא עדכון/מחיקה לאף תפקיד.

## 4. מפרט טופס הזמנה (מאמץ את האבטיפוס + השלמות)

**בלוק 1 — פרטי לקוח:** שם*, טלפון*, סוכן* (נבחר אוטומטית לפי המשתמש המחובר — לא הקלדה חופשית כמו היום), כתובת*, מספר הזמנה (read-only; "טיוטה" עד סנכרון). חדש: חיפוש לקוח קיים / קישור לליד — עם אפשרות "לקוח חדש" מהירה כמו היום.

**בלוק 2 — מידות וילונות (סגול):** כרטיסי פריטים + "הוסף וילון". מודל הוספה: מיקום, סוג תפירה, רוחב, גובה, מכפלת, שטייף, סוג בד (בחירה מהקטלוג עם חיווי זמינות מלאי ✅/⚠️/❌ + אפשרות טקסט חופשי), חצוי, לביצוע, עלות ₪, סטטוס, הערות.

**בלוק 3 — זברות/ונציאני/רומי/גלילה (כתום):** סוג פריט, מיקום, **רגלי קיר/תקרה, צד מנגנון** (מוחזרים), רוחב, גובה, צבע/סוג בד, לביצוע, עלות ₪, סטטוס, הערות.

**בלוק 4 — תשלום (ירוק):** toggle "הצעת מחיר בלבד"; ארבע תיבות סיכום חי — סה"כ פריטים לביצוע ₪ / סה"כ רוחב (מטר קיר, סכום רוחבי הפריטים לביצוע בהמרה למטרים) / חישוב אוטומטי ₪ / נשאר לתשלום ₪; שדות: התקנה, הנחה, סה"כ לתשלום* + כפתור "מלא", שולם על החשבון*, סוג תשלום, אימייל לשליחה, הערות, חתימה.

**שליחה:** דיאלוג שני המסלולים → יצירת PDF → שליחה למייל (ובהמשך WhatsApp) → רישום ב-communications → מעבר לסטטוס המתאים. באופליין: נשמר כטיוטה בתור, נשלח אוטומטית כשחוזרת רשת.

## 5. זרימת מלאי משולבת (סיכום ההחלטה)

קליטה: שקילת גליל (ברקוד + משקל) → תנועת receipt. הזמנה נשמרת → שריון = Σ estimated_meters של פריטים לביצוע (חישובי, לא תנועה). פריט מסומן "נגזר" → דיאלוג בחירת גליל + מטרים בפועל (ממולא מראש) → תנועת consumption. ספירה: שקילה → תנועת adjustment על ההפרש. זמין = פיזי − משוריין; מוצג לסוכן כחיווי בבחירת בד.

**תלות פתוחה:** נוסחת estimated_meters לכל משפחת מוצר (ראה סעיף 8.1). עד שתוגדר — שדה ידני עם ברירת מחדל = רוחב הפריט.

## 6. ארכיטקטורה טכנית (ללא שינוי מגרסה 1.0, בתוספת אופליין)

React (Vite) + TypeScript + Tailwind, PWA. Supabase: Postgres+RLS, Auth, Storage (תמונות בדים, PDF), Edge Functions (הקצאת מספר הזמנה אטומית, יצירת PDF, Webhook לידים מ-Make). Cloudflare Pages + דומיין. Make: Sheets→לידים, שליחת Email/WhatsApp.

**שכבת אופליין:** IndexedDB (Dexie) — עותק קריאה של קטלוג+תמונות מוקטנות ולקוחות אחרונים; תור טיוטות הזמנה; סנכרון ברקע עם ניהול התנגשויות פשוט (הזמנה שייכת לסוכן יוצרה — קונפליקטים נדירים). מספר ההזמנה הרשמי נקבע רק בסנכרון — מונע כפילויות מספור.

**PDF בעברית:** יצירה בצד שרת מ-HTML template (RTL מלא, פונט עברי) דרך שירות רינדור ב-Edge Function/Worker — נקבע סופית בשלב 5 מול תבניות ה-PDF הקיימות שתעביר.

## 8. פתוח לסגירה (רשימה סופית)

1. **נוסחת צריכת בד** פר משפחת מוצר — לשריון המלאי. אפשר גם כלל אצבע ("רוחב × 2 בווילון קפלים") — נעדיף כלל פשוט שעובד על כלום.
2. **אישור:** התקנה לא נכללת בחישוב האוטומטי — מכוון?
3. **שטייף** ו**חצוי** — משפט הסבר (לא חוסם סכמה, כן חוסם ניסוח נכון בטופס וב-PDF).
4. **גיליון6 / גיליון7 / מעקב תאריכים** — רלוונטיים או ארכיון?
5. **רשימת סוגי התשלום** המלאה (ראיתי: אשראי; מהגיליון: סוג תשלום — מה הערכים?).
6. **דוח יומי** — מה הוא כולל היום (ראיתי כפתור באבטיפוס)?
7. חומרי שלב 0: ייצוא FABRIKAIRI, גיליון לידים, 2–3 PDF קיימים, דומיין+Cloudflare.
