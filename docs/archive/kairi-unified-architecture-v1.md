## 2. מודולים עיקריים

**M1 — CRM לידים ולקוחות** (מחליף את MK MINI CRM)
קליטת לידים מ-Google Sheets (סנכרון אוטומטי), רשימת לידים עם סטטוסים, פעולות מהירות (חיוג, WhatsApp, שיוך לסוכן), המרת ליד ללקוח, כרטיס לקוח עם היסטוריה מלאה — הצעות, הזמנות, מסמכים ותקשורת.

**M2 — קטלוג בדים ופריטים** (מחליף את FABRIKAIRI)
כרטיס בד: תמונות, מק"ט, ספק, מחיר, רוחב גליל, הרכב, תגיות, זמינות. חיפוש וסינון מהיר בשטח (מותאם מובייל), גלריית תמונות, וסטטוס פעיל/לא פעיל. זהו מקור האמת היחיד לבדים — טפסי הזמנה שולפים ממנו.

**M3 — הצעות מחיר והזמנות** (מחליף את KAIRI CURTAINS NEW TOFSY)
טופס בשטח: בחירת לקוח (או יצירה מהירה), שורות מוצר — כל שורה עם סוג מוצר, בד מהקטלוג, מידות, כמות ופרמטרים — מנוע תמחור עם כללי חישוב (לפי רוחב/גובה/מקדם תפירה וכו'), הנחות, סיכום, ושמירה כטיוטה/הצעה/הזמנה.

**M4 — מסמכים ושליחה**
יצירת PDF מהצעה/הזמנה בעברית מלאה (RTL), שמירת המסמך ב-Storage וקישורו לישות, שליחה ב-WhatsApp וב-Email (בשלב ראשון דרך Make), ותיעוד כל שליחה ביומן תקשורת.

**M5 — מעקב ביצוע**
סטטוסים לאורך חיי ההזמנה (התקבלה → מדידה → ייצור/תפירה → מוכן → התקנה → הושלם), לוח מעקב לפי סטטוס, היסטוריית שינויים, והתראות (בהמשך).

**M6 — ניהול והגדרות** (חדש, רוחבי)
ניהול משתמשים ותפקידים, מחירונים וכללי תמחור, תבניות PDF, הגדרות אינטגרציות (Webhooks ל-Make), ויומן פעולות (Audit Log).

## 4. קשרים בין המודולים

- **CRM → הזמנות:** מכל ליד/לקוח אפשר לפתוח הצעה/הזמנה בלחיצה; ההזמנה יורשת את פרטי הלקוח.
- **קטלוג → הזמנות:** כל שורת מוצר מפנה ל-`fabric_id`. המחיר נשלף מהקטלוג בזמן היצירה **ומוקפא בשורה** — שינוי מחיר עתידי בקטלוג לא משנה הזמנות קיימות.
- **הזמנות → מסמכים:** יצירת PDF נשענת על נתוני ההזמנה + תבנית; המסמך נשמר ומקושר.
- **מסמכים → CRM:** כל שליחה נרשמת ב-`communications` ומופיעה בכרטיס הלקוח.
- **הזמנות → מעקב:** שינוי סטטוס נרשם ב-history ומזין את לוח המעקב.
- **הכול → הרשאות:** Row Level Security לפי role (למשל: Sales רואה את הלידים שלו, Office רואה הכול, רק Admin מוחק).

## 5. זרימת העבודה המרכזית

```
Google Sheets ──(Make webhook / סנכרון)──▶ ליד חדש ב-CRM
      ליד ──(שיוך לסוכן, יצירת קשר)──▶ סטטוס מתעדכן
      ליד ──(המרה)──▶ לקוח
      לקוח ──▶ הצעת מחיר: בחירת מוצרים + בדים מהקטלוג + מידות
      מנוע תמחור ──▶ סיכום ▶ שמירה
      הצעה ──▶ PDF (עברית/RTL) ──▶ שליחה בWhatsApp/Email ──▶ נרשם ביומן
      הצעה מאושרת ──▶ הזמנה ──▶ מעקב סטטוסים ──▶ הושלם
```

נקודות קריטיות בזרימה: מניעת כפילות לידים בסנכרון מ-Sheets (לפי external_id + טלפון), הקפאת מחירים בשורות, מספור מסמכים רץ ועקבי, ותיעוד כל שליחה ללקוח.

## 6. המלצת Stack

### ההמלצה: **React (Vite) + Supabase + Cloudflare Pages**, עם Cloudflare Worker אחד לשירותי צד-שרת

| רכיב | בחירה | תפקיד |
|---|---|---|
| Frontend | React + Vite + TypeScript + Tailwind + shadcn/ui | SPA מהיר, מותאם מובייל לשטח. קרוב מאוד למה ש-Lovable מייצר — מקל על מיחזור קוד קיים |
| Database | Supabase (Postgres) | טבלאות, קשרים, RLS להרשאות |
| Auth | Supabase Auth | Email+סיסמה או Magic Link, טבלת roles |
| Storage | Supabase Storage | תמונות בדים + קבצי PDF |
| API לצד שרת | Supabase Edge Functions או Cloudflare Worker | יצירת PDF, Webhooks נכנסים מ-Make/Sheets, לוגיקה רגישה |
| Hosting | Cloudflare Pages | דומיין אמיתי, SSL, CDN, deploy אוטומטי מ-GitHub |
| אוטומציות | Make | WhatsApp, Email, סנכרון Sheets — בלי לכתוב אינטגרציות מאפס |

למה זה הכי מתאים לכם: עלות כמעט אפסית בקנה המידה הזה (Cloudflare Pages חינם, Supabase Free/Pro ~0–25$ לחודש), Postgres אמיתי עם יכולת ייבוא נתונים קיימים, קוד Lovable קיים כנראה כבר React+Supabase כך שחלקו ניתן למחזור, ו-RLS נותן הרשאות ברמת הנתונים בלי לבנות backend שלם.

### 7. השוואת החלופות

**חלופה A — React (Vite) + Supabase + Cloudflare Pages (מומלץ)**
יתרונות: פשוט, זול, מהיר לפיתוח, Auth+Storage+DB מוכנים, תואם לקוד Lovable, קל למצוא מפתחים להמשך. חסרונות: SPA ללא SSR (לא רלוונטי למערכת פנימית), תלות בספק Supabase (מרוככת בכך שזה Postgres סטנדרטי שניתן להוציא בכל רגע).

**חלופה B — Next.js + Supabase + Cloudflare**
יתרונות: SSR, framework עשיר. חסרונות: SSR לא נותן שום ערך למערכת פנימית מאחורי login; הרצת Next.js על Cloudflare דורשת אדפטרים (OpenNext) שמוסיפים שכבת סיבוך ותקלות deploy. מורכבות בלי תמורה — לא מומלץ כאן.

**חלופה C — Cloudflare Workers + D1 + Hono**
יתרונות: הכול אצל ספק אחד, זול, מהיר. חסרונות: D1 הוא SQLite — בלי RLS, בלי Auth מובנה, בלי Storage לתמונות (צריך R2 בנפרד), והרבה יותר קוד תשתית לכתוב בעצמנו (הרשאות, ניהול משתמשים, uploads). מתאים למוצרי API, פחות למערכת ניהול פנימית שצריכה לקום מהר.

**חלופה D — Retool / פלטפורמת Internal Tools**
הוגן לציין: למערכת פנימית טהורה זו אופציה מהירה. חסרונות: עלות פר-משתמש, פחות שליטה בחוויית שטח במובייל, ונעילה לפלטפורמה — בדיוק הבעיה שממנה אתם יוצאים עכשיו עם Base44. לא מומלץ.

## 8. תוכנית Migration מהאפליקציות הקיימות

**עיקרון: מהגרים נתונים, לא קוד.** קוד מ-Base44 בנוי סביב ה-SDK שלהם ולא ירוץ מחוץ לפלטפורמה; קוד Lovable יכול לשמש כרפרנס ל-UI ולוגיקת חישוב, אבל המערכת החדשה נבנית נקייה. מה שחייב לשרוד הוא **הנתונים, כללי התמחור, ומבני הטפסים**.

שלבי המיגרציה לכל אפליקציה:

**FABRIKAIRI (בדים) — עדיפות ראשונה לנתונים.**
ייצוא כל הרשומות (CSV/JSON מתוך Base44 Data או דרך ה-API שלהם), הורדת כל התמונות (סקריפט שמוריד לפי URL), טעינה ל-Supabase: טבלת fabrics + העלאת תמונות ל-Storage + קישור. בדיקת שלמות: מספר רשומות, תמונות חסרות, כפילויות מק"ט.

**MK MINI CRM (לידים).**
מקור האמת האמיתי הוא כנראה Google Sheets — ולכן ייתכן שאין צורך לייצא מהאפליקציה עצמה אלא לייבא ישירות מהגיליון. נמפה עמודות גיליון ↔ שדות `leads`, נגדיר external_id, ונבנה את הסנכרון השוטף כבר מהיום הראשון (Make → Webhook → DB).

**KAIRI CURTAINS NEW TOFSY (הזמנות).**
החשוב ביותר כאן אינו הדאטה אלא **הלוגיקה**: רשימת סוגי המוצרים, כל שדות הטופס לכל מוצר, ונוסחאות התמחור המדויקות (כולל מקרי קצה — מינימום חיוב, מקדמי תפירה, עיגולים). הזמנות היסטוריות — אם ניתנות לייצוא, נטען לטבלת `orders` עם דגל "legacy"; אם לא, נשמור PDF-ים קיימים כארכיון ב-Storage.

סדר בטוח: המערכות הישנות ממשיכות לעבוד במקביל עד שכל מודול חדש עולה ומאומת, ואז מכבים מודול ישן אחד בכל פעם. אין רגע של "מעבר הכול בבת אחת".

## 9. סדר עבודה מומלץ (Roadmap)

**שלב 0 — Discovery וייצוא (לפני קוד):** איסוף כל החומרים מסעיף 10, כתיבת מפרט תמחור מדויק, אימות מה ניתן לייצא מ-Base44.

**שלב 1 — תשתית:** ריפו GitHub, פרויקט Supabase, סכמת DB מלאה + RLS, Auth עם 4 תפקידים, שלד אפליקציה (ניווט, layout, RTL), pipeline ל-Cloudflare Pages עם דומיין. *תוצר: מערכת ריקה באוויר עם login.*

**שלב 2 — קטלוג בדים + מיגרציית נתונים:** המודול הכי עצמאי והכי שמיש מיד. *תוצר: כל הבדים במערכת החדשה, שמישה בשטח.*

**שלב 3 — CRM לידים:** מסכי לידים, סטטוסים, פעולות מהירות, סנכרון Google Sheets דרך Make, המרה ללקוח. *תוצר: אפשר לכבות את MK MINI CRM.*

**שלב 4 — הצעות והזמנות:** מנוע תמחור, טפסים לפי סוגי מוצר, שליפת בדים מהקטלוג. זה השלב הכבד ביותר — נעשה מוצר-מוצר. *תוצר: יצירת הזמנה מלאה בשטח.*

**שלב 5 — PDF ושליחה:** תבנית PDF בעברית, שמירה ב-Storage, שליחה ב-WhatsApp/Email דרך Make, יומן תקשורת. *תוצר: אפשר לכבות את Tofsy.*

**שלב 6 — מעקב, הרשאות, ליטוש:** לוח מעקב סטטוסים, חידוד RLS, audit log, ביצועים, גיבויים.

הערכת גודל גסה: שלבים 1–2 הם הקצרים; שלב 4 הוא כמחצית מהעבודה הכוללת בגלל התמחור. נדייק הערכות אחרי שלב 0.

## 10. מה בדיוק להעביר לי מכל אפליקציה

**מכל שלוש האפליקציות (חובה):**
1. צילומי מסך של **כל מסך ומסך**, כולל מצבי עריכה, מודלים וטפסים פתוחים.
2. סרטון קצר (אפשר הקלטת מסך מהטלפון) של תהליך עבודה מלא אחד באפליקציה.
3. רשימת "מה עובד טוב שחייב להישאר" ו"מה שבור/מעצבן" — בנקודות חופשיות.

**FABRIKAIRI (Base44):**
4. ייצוא נתונים: ב-Base44 → Data/Entities → Export (CSV/JSON) לכל ישות. אם אין כפתור ייצוא — צילום מסך של הגדרת כל Entity עם כל השדות, ואמצא דרך דרך ה-API.
5. הערכה כמה בדים וכמה תמונות יש (סדר גודל).

**MK MINI CRM:**
6. קישור/עותק של גיליון ה-Google Sheets של הלידים (או צילום שורת הכותרות + 2–3 שורות דוגמה בהשחרת פרטים).
7. איך לידים נכנסים לגיליון היום (טופס? ידני? קמפיין?), והאם קיים תרחיש Make פעיל — אם כן, צילום מסך של התרחיש.

**KAIRI CURTAINS NEW TOFSY:**
8. אם זה Lovable — ייצוא הקוד ל-GitHub (Lovable מאפשר GitHub sync) ושיתוף הריפו או קבצים מרכזיים: components של הטפסים, קובץ חישובי המחיר, סכמת Supabase אם יש (`supabase/migrations` או צילום הטבלאות).
9. **מסמך תמחור**: רשימת כל סוגי המוצרים, ולכל אחד — אילו שדות ממלאים ואיך מחושב המחיר, כולל דוגמה מספרית אחת מלאה לכל מוצר. זה המסמך הכי קריטי בכל הפרויקט.

## שאלות פתוחות לדיון

1. **תמחור:** האם המחירים ללקוח הם קבועים לפי נוסחה, או שהסוכן משנה ידנית בשטח? (משפיע על הרשאות ועל מבנה הטופס.)

3. **מספור מסמכים:** האם יש היום מספור רץ שחייבים להמשיך ממנו (למשל להתחיל מ-1547 ולא מ-1)?

5. **אופליין:** האם סוכן בשטח נתקל באזורים בלי קליטה, וצריך יכולת עבודה אופליין חלקית? (משפיע מהותית על הארכיטקטורה — עדיף לדעת עכשיו.)
